# Production readiness and operator runbook

This repository is a tested draft storefront. It has not been deployed or certified for live payments. Keep `COMMERCE_LIVE=false` until the following business, infrastructure and acceptance work is complete.

## Commercial launch requirements

- Replace the six concept listings with approved real products, actual photography, validated specifications, SKU/variant design, prices, stock and market availability. Current artwork is local SVG illustration; an upload/media service and variant-level inventory are not implemented.
- Supply the merchant's legal entity, address, support channels, supported markets, dispatch and delivery estimates, customs responsibility, returns, warranty, refund terms, privacy contacts and data-retention schedule. Replace the draft legal pages with approved policies. Obtain applicable legal/tax advice.
- Configure explicit `SHIPPING_RATES_JSON` destination/currency pairs in minor units. No destination is implicitly supported. Rates are flat per order; carrier-calculated rates, duties and tax-inclusive pricing are not implemented.
- Complete provider onboarding. USD card payments require an eligible Stripe merchant account. KES M-Pesa requires a Daraja-enabled merchant shortcode and callback setup. No live credentials are included in the repository.
- Set `TAX_POLICY_APPROVED=true` only after verifying the Stripe Tax configuration and all supported markets. For M-Pesa, additionally set `MPESA_TAX_APPROVED=true` and `MPESA_TAX_BASIS_POINTS` to the approved rate for the entire order including shipping. A single flat rate is intentionally limited; mixed tax treatments require a dedicated tax integration before selling those products.

## Deployment

1. Use a supported Node.js runtime and HTTPS hosting. Configure `APP_ORIGIN` exactly; state-changing browser endpoints reject other origins. Do not rely on preview-domain wildcards. Set runtime secrets securely; inspect presence only. The app transforms M-Pesa credentials locally and uses local HMAC secrets, so proxy-only placeholder secrets cannot replace raw runtime bindings for those values.
2. Use a private MongoDB replica set or sharded cluster with TLS, least-privilege credentials, backups and restore testing. Permit network access using supported hosting/cloud networking. Never disable TLS verification. Run `npm run db:prepare` in an explicit migration window. It creates unique/TTL indexes; duplicate-data conflicts require investigation, never automatic deletion. Existing demo `orders` documents lack the new schema fields and need a separate reviewed migration or archival plan. Do not reuse a production database without that review.
3. Set `CHECKOUT_COOKIE_SECRET`, independent `ADMIN_SESSION_SECRET`, `ADMIN_PASSWORD_HASH`, provider keys and `CRON_SECRET`. Rotate the admin password hash to invalidate existing admin sessions. Restrict `/admin` and `/api/admin/*` at a hosting access gateway with MFA and audit logs. The application currently has a single operator role, an eight-hour signed cookie, shared durable login throttling and no account recovery flow.
4. Run `npm ci`, unit checks, production build, isolated integration and browser checks. Configure `/api/health` for monitoring; it reports preview mode or database ping only, not provider authorization or overall operational readiness. Keep preview deployments non-indexable. Pages and CSP nonces render dynamically.
5. Create a Stripe webhook endpoint at `/api/payments/stripe/webhook` for `checkout.session.completed`, `checkout.session.expired` and `checkout.session.async_payment_succeeded`. Set `STRIPE_WEBHOOK_SECRET` and `STRIPE_SECRET_KEY`. Match the endpoint's API version with the SDK. Enable/configure Stripe Tax and default tax codes. Use Stripe sandbox payments, replayed/duplicate events, failed payments and expired sessions in a staging environment before live activation. No remote Stripe session or real charge was initiated in development validation.
6. Configure `MPESA_ENV=sandbox` initially; `production` selects the production endpoint. Set the consumer key/secret, shortcode, passkey and `MPESA_TRANSACTION_TYPE` (typically `CustomerPayBillOnline`; verify against your merchant account). `MPESA_CALLBACK_URL` must be public HTTPS with a URL-encoded token matching `MPESA_CALLBACK_TOKEN` (24+ characters). Redact callback query strings at the host/proxy and restrict log access. Configure provider egress for sandbox.safaricom.co.ke or api.safaricom.co.ke as appropriate. Built-in fetch/SDK network access must be verified on your host; this app does not bypass cloud egress controls.
7. Schedule an authenticated GET to `/api/internal/reconcile` at least every minute with `Authorization: Bearer <CRON_SECRET>`. The repository does not create a hosting schedule. The route processes bounded batches, expires abandoned reservations, and holds uncertain records. Monitor job failures, backlogs, unmatched callbacks, review payments and stock anomalies. Never put the cron secret in a URL.
8. Configure transactional email and support operations before public launch. Set `RESEND_API_KEY` and a verified `EMAIL_FROM` for the durable notification worker, permit api.resend.com egress, and validate delivery, duplicate-event behavior, bounced messages and sender-domain authentication in staging. Receipt/fulfillment outbox rows commit with the order transaction; missing configuration leaves them queued. Failed permanent sends or uncertain deliveries older than 23 hours are held for review. Monitor `emailoutboxes` and provider logs, set retention, and never blindly requeue an uncertain send after provider idempotency expires. The current order confirmation/tracking is browser-session scoped; it does not support cross-device recovery. Maintain a refund/dispute process through provider dashboards; refund event ingestion, automatic restocking after refund and a returns portal are not implemented.
9. Configure edge-level rate limiting for order creation, payment initiation, sign-in and webhooks. Application limits are durable per guest token, so a bot can rotate guest tokens; use your trusted host's verified client identity and controls. Do not trust arbitrary forwarded IP headers. Monitor and protect public asset and page traffic as well.
10. Complete provider-backed staging tests, accessibility review with representative users, performance/load testing, alert routing, privacy/security review, backup restore drills and incident response rehearsal. Only then activate live commerce. Publication of a development environment is not deployment of this site.

## Payment recovery

- A payment return URL never marks an order paid. A verified provider event does.
- M-Pesa initiation timeouts hold stock and payment for operator review. Do not resend an STK prompt. Check Daraja/provider records and merchant statements. Stale `initiating` records move to review after five minutes; review records are not auto-released.
- Callback evidence is retained in `callbackinboxes`. A callback arriving before initiation identifiers are written is attached by scheduled reconciliation. Conflicting or unmatched evidence requires investigation. Configure retention for this personal data; no automatic TTL deletes payment evidence.
- If Stripe creates a checkout session but the app cannot persist its ID, the order remains reserved. Recover using provider metadata and the stable `checkout-<orderId>` idempotency key before considering release. A missing session ID is never proof that payment did not happen. Do not retry session creation after the provider's idempotency retention period without verifying records.
- A paid Stripe session with a missing/delayed webhook stays reserved; the cron reports `webhookRequired`. Replay the signed provider event after investigating, rather than manually asserting payment success.
- Expired Stripe sessions release stock once; completed events for cancelled/released orders become review cases. Investigate any out-of-order contradictory provider events before fulfillment.
- Failed, definitively reconciled M-Pesa payments cancel the order and release its stock in the same transaction. A new order is needed to retry after definitive failure.
- Confirm receipts/settlement independently before irreversible fulfillment. Never change application records based only on customer screenshots.

## Known scope limits

No customer account system, refunds portal, card disputes automation, product variants, search index, media upload service, coupons, reviews, tax jurisdictions engine for M-Pesa, carrier integration, multi-warehouse stock, multi-operator audit UI or admin MFA inside the app. Only USD and KES are supported; there is no live currency conversion. The admin list shows 100 recent orders. These are explicit scope limits, not completed production capabilities.
