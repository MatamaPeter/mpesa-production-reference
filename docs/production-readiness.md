# Release acceptance and operator runbook

Keep `COMMERCE_LIVE=false` until acceptance is complete. `COMMERCE_STAGE` must be explicitly `sandbox` or `live` when checkout is enabled. Sandbox rejects production payment credentials. `npm run check:production` evaluates live configuration without enabling checkout. It is a static gate, not provider acceptance.

## Merchant acceptance

Approve real products, stock, licensed media, specifications, warranty terms and market prices. The six preview listings are fixtures. Confirm the legal entity, registration details where applicable, customer support staffing, shipping charges/timelines, return eligibility, privacy/retention/processor terms and tax obligations. The configured Kenyan shipping/returns copy is a proposed draft. Review the whole policy text, remove draft qualifications only after approval and set `site.policy.approved=true`.

Launch destinations are Kenya. Add countries/currencies only with approved logistics, prices, tax treatment and provider eligibility. A Stripe integration does not establish that a Kenyan or other legal entity is eligible for a Stripe account. Confirm onboarding directly; do not use another merchant's credentials.

## Infrastructure and owner provisioning

1. Provision HTTPS hosting and set `APP_ORIGIN` to its exact origin. Configure deployment secrets using `.env.example`. Use independent random session and worker secrets; `AUTH_ENCRYPTION_KEY` is 32 random bytes encoded as 64 hexadecimal characters. Back it up securely: losing it prevents decryption of enrolled authenticators. Never log keys or put them in public configuration.
2. Provision private TLS MongoDB with transaction support, least-privilege access and tested point-in-time backups. Resolve the configured hostname/SRV records from the runtime before investigating authentication. Do not disable TLS verification. Review existing data and take a backup, then run `npm run db:prepare` in an explicit change window. Duplicate index conflicts need investigation, not automatic deletion. This version adds models and coordination/warehouse records; legacy order migration is not automatic.
3. Configure Resend with a verified sender, enable `ACCOUNT_AUTH_ENABLED=true`, and test delivery. In a protected provisioning window, temporarily enable `ADMIN_BOOTSTRAP_ENABLED=true` and configure `ADMIN_SESSION_SECRET` plus a salted hash generated by `scripts/admin-password.mjs`. Supply the password through secure stdin, not shell arguments/history. Sign in through `/admin`. Have the intended owner verify their account email; use the staff panel to assign that existing account the owner role. The owner enrolls an authenticator under `/account`, saves recovery codes privately and verifies a code. Confirm normal staff access, then disable bootstrap and remove its password/session secrets. The live gate rejects enabled bootstrap.
4. Deploy the web service and a supervised worker. The Dockerfile uses a standalone non-root runtime. In the image, worker command is `node scripts/worker.mjs`; outside it, `npm run worker`. Set `WORKER_APP_ORIGIN` to the service, `CRON_SECRET` identically in both, and tune `WORKER_INTERVAL_MS`/`WORKER_CONCURRENCY` from measured backlog. Alternatively schedule authenticated GET `/api/internal/reconcile` at least every minute. Secrets belong in the Authorization header, never URLs. Do not run both modes accidentally without sizing their provider traffic.
5. Enable hosted logging with PII/query-string redaction, metrics, paging, edge bot/rate controls and database backup monitoring. `/api/health` reports liveness/database ping, not full readiness. `/api/admin/readiness` requires audit permission and reports owner, topology, heartbeat and review-queue conditions. Monitor queue age and failure counts independently: a worker heartbeat alone does not prove every job succeeded.

## Provider acceptance

- **Stripe:** configure test keys and a signed endpoint at `/api/payments/stripe/webhook`. Subscribe to `checkout.session.completed`, `checkout.session.expired`, `checkout.session.async_payment_succeeded`, `refund.created`, `refund.updated`, `charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed`. Match the endpoint API version to the installed SDK. Test successful/failed/expired payments, duplicate/reordered events, address/tax calculation, partial/full refunds, asynchronous refund status and disputes. Configure merchant tax registrations and product tax codes; verify real supported markets before setting `TAX_POLICY_APPROVED=true`. Then switch to independently accepted live keys and webhook secret.
- **M-Pesa:** use sandbox first. Set consumer credentials, shortcode, passkey, transaction type, callback URL/token and approved Kenyan tax settings. `MPESA_CALLBACK_URL` must be public HTTPS with its URL-encoded token matching `MPESA_CALLBACK_TOKEN`; redact callback query strings at the proxy. Validate initiation, immediate/early callbacks, signed-in and guest access, failed PIN/cancellation, timeouts and query reconciliation. OAuth success alone does not validate shortcode/passkey, callbacks or settlement. Set production mode only after merchant approval and a controlled end-to-end acceptance transaction.
- **Tax:** fixed-rate M-Pesa requires explicitly approved basis points including shipping. Optional `MPESA_TAX_PROVIDER=stripe` uses expiring Stripe Tax quotes; test rounding and set `MPESA_ROUNDING_APPROVED=true` only after approval of whole-KES charging. Monitor tax jobs and review partial-refund adjustments. Tax integration does not file returns or approve treatment.
- **Email:** verify sender domain, SPF/DKIM/DMARC, account-link and receipt delivery, retries, duplicates, bounces and support replies. Restrict sandbox delivery with `EMAIL_SANDBOX_RECIPIENT`. Do not enable public accounts without reliable delivery.
- **Shipping:** configure warehouse dispatch addresses and optional `SHIP_FROM_ADDRESS_JSON` fallback. Shippo quotes/labels are operator workflows; checkout shipping rates remain approved fixed amounts from `SHIPPING_RATES_JSON`. Test label purchase with a test token before setting `SHIPPING_LABEL_PURCHASE_ENABLED=true`; enable tracking separately. Validate carrier service, dimensions, weights, address format, international customs and refunds/cancellations through carrier procedures. Ambiguous paid label requests require review, not automatic retries.
- **Media/FX:** validate GridFS backups or S3 object access/permissions, sanitized uploads and restore. Optional FX requires current rates, currency support, stale-rate failure tests and worker materialization. Default fixed prices need no FX provider.

Never infer successful delivery, merchant eligibility or settlement from the presence of a key. Provider calls can move real money; use test credentials until the acceptance plan authorizes controlled live tests.

## Payment and inventory recovery

A redirect never marks payment complete. Release stock only from definitive evidence. M-Pesa timeouts and interrupted initiation hold stock; do not resend an STK request. Use the recovery queue to recheck callback/query evidence. A no-charge release requires two different named authorized operators and evidence references. Bootstrap access cannot provide dual confirmation. Verify merchant records independently; a screenshot is insufficient.

If Stripe created a session but its ID was not persisted, investigate provider metadata and the stable `checkout-<orderId>` idempotency key. Missing local IDs are not proof of no charge. Replay the provider's signed event after investigation. Do not retry creation after the provider idempotency window without checking its records. Late completion for a released order must remain a review case rather than trigger fulfilment.

Refund reservations cap pending plus completed refunds at the paid balance. Stripe refund jobs retry with a stable idempotency key inside the safe window; pending provider results await signed events. Delayed/conflicting events require provider review and replay. M-Pesa manual refunds require separate initiator/confirmer and a real transaction reference; this app does not call a B2C reversal API. Receipt of returned stock is recorded separately and exactly once. Never refund and assume goods were physically returned.

Email, label, refund and tax records in review need a named owner. Do not blindly retry after provider idempotency windows expire. Email queue views omit message bodies and authentication tokens; follow sender-provider records without exposing sign-in links. Disputes hold fulfilment; submit evidence and reconcile settlement in the payment-provider dashboard. Currency analytics are separate totals, not audited revenue or bank settlement reports.

## Release, capacity and rollback

Run unit/type/build/format checks, isolated integration, supported browser/accessibility tests and deployment-specific capacity tests. The local 1,000-virtual-shopper browsing result is documented in `validation.md`; repeat a sustained distributed test on the actual HTTPS/CDN/database/worker topology. Include authenticated browsing, hot-SKU checkout contention, write latency, worker recovery and provider sandbox limits. Do not issue uncontrolled live payments during load tests.

Exercise backup restore into a separate environment, crashed/restarted workers, webhook replay, provider outage, database failover and secret rotation. Define availability/latency/error budgets and page the responsible operators. Retain a previous immutable image and reviewed schema compatibility plan. To halt new checkout, set `COMMERCE_LIVE=false`; continue authorized webhook/recovery processing for outstanding payments. Never roll a database back blindly after external money movements. Reconcile before reopening.

Before go-live: complete the commercial approvals, pass static and private readiness, resolve review queues, record provider-backed acceptance, verify operational alerts and backups, and obtain the merchant's release decision. No Google/Amazon certification or zero-failure guarantee is asserted.
